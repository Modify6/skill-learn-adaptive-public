Linux epoll：挨个去问 · 有事按铃

治「万级连接下 CPU 全被无脑遍历吃光、每次调用重复在内核拷贝大数组」—— 让 Linux 服务器从 select 的「班主任挨个点名」进化到 epoll 的「前台门铃秒级取件」。透视红黑树与就绪链表的底层协作。

时代演进：select/poll ＝ 每次拷全量数组入内核 + 盲目 O(N) 挨个巡检，万级连接直接累死！ ｜ epoll ＝ 内核常驻红黑树 + 网卡硬件中断挂就绪链表，O(就绪数) 极速返回！  ‖  两个核心零件：红黑树（RB-Tree）（高效管理上万个监听连接，增删改查 O(log N)） · 就绪双向链表（rdllist）（只有活跃连接才会被挂进来，wait 只看链表）。
系统调用 / 机制物理上是什么生活同类 / 绰号解决的核心麻烦
select / poll用户态传入 fd_set 数组，内核遍历 0 到 N-1 查状态班主任每天把一万个学生挨个问一遍：“你写完了吗？”N 很大但活跃极少时，99.9% 的 CPU 耗在无用空转上
epoll_create(1024)在内核空间分配一块专用的 eventpoll 结构体（含红黑树+就绪链表）“在内核开一间快递收发室”建立内核常驻大本营，摆脱每次调用都要重复传输 fd 数组的痛点
epoll_ctl(ADD/DEL/MOD)往内核的红黑树中添加/删除/修改监控的 socket 文件描述符把学生的学号登记到前台名册上（只登一次）增删查改均为 O(log N)，内核牢牢记住所有监听对象
epoll_wait(events, max)检查就绪链表（rdllist），非空直接拷出；为空则挂起进程休眠坐等门铃响，前台推着装满快件的小推车直接出来交接复杂度降为 O(活跃数)！无论管 1 万还是 100 万连接，瞬间秒回！
LT 水平触发 (默认)只要 socket 缓冲区还有未读完的数据，每次 wait 就会一直报警操心的老妈：“你碗里还有半碗饭！快吃！快吃！”防漏读，安全简单，但可能触发过多次无谓通知
ET 边缘触发 (EPOLLET)只在数据“从无到有”的状态跳变瞬间通知一次！快递门铃只叮咚响一声，绝不按第二下极致性能，但必须搭配非阻塞 IO 且 while 循环读到 EAGAIN！

🔍 为什么 select 最多只支持 1024 个连接？

select 底层使用的是固定长度的位图（Bitmask，fd_set），在 <sys/select.h> 中宏写死了 FD_SETSIZE = 1024。更要命的是，每次调用都必须重新将这 1024 位的位图全量拷入内核，极度昂贵！

🌳 为什么 epoll 采用红黑树而不是哈希表？

因为监控的 FD 数量是动态变化的，哈希表在发生扩容（Rehash）或内存分配时可能产生难以预测的高延迟，且哈希表需要预分配巨大桶内存。红黑树兼具 O(log N) 的严格查找/增删性能 和 极小内存开销，不会发生卡顿抖动。

⚡ ET 边缘触发为什么必须死磕非阻塞 IO？

因为 ET 模式在数据到达时只按一次门铃！如果你用阻塞的 read() 循环读，当最后一次把数据读空时，阻塞 read() 会让整个工作线程彻底卡死；而如果不循环读干，剩余数据再也不会触发通知，产生灾难性死锁！

Linux epoll 核心三步：epoll_create 建立内核大本营 → epoll_ctl 红黑树增删改查 → epoll_wait 就绪链表极速取件 ｜ 从此终结 C10K 噩梦
