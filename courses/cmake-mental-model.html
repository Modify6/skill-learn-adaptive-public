Modern CMake：生成器不是编译器 · 一切皆 Target

治「跨平台编译脚本各写一套、全局变量污染到处穿透、PRIVATE/PUBLIC 傻傻分不清」—— 从手敲编译命令的灾难出发，掌握基于 Target（目标）与属性传递的现代构建心智模型。

核心定性：CMake 本身不编译任何一行 C/C++ 代码（它是元构建生成器），它读取平台无关的 CMakeLists.txt，生成特定平台的 Makefile/Ninja。  ‖  黄金心智法则：一切皆 Target（add_executable / add_library），彻底淘汰全局变量；通过 PRIVATE · INTERFACE · PUBLIC 精确控制属性传递链条。
指令 / 概念物理上是什么本质角色核心职责与法则
cmake -B build配置与生成阶段：解析 CMakeLists.txt，产出 Makefile / Ninja 脚本生成器（Generator）在此阶段不调用编译器，只做环境检测与构建规则生成
cmake --build build执行构建阶段：驱动底层 make/ninja 调用 g++/clang 编译代码真正的编译执行跨平台编译统一入口，免去手动敲 make 或 msbuild 的差异
add_executable / add_library在 CMake 内存中注册一个 Target 实体（可执行文件或库）创建目标实体现代 CMake 的一等公民，后续所有配置都挂载在具体 Target 上
target_include_directories给 Target 的属性背包塞入头文件搜索路径（-I 目录）装配头文件背包取代老旧全局的 include_directories()，杜绝路径污染
target_link_libraries建立 Target 之间的依赖边，并顺带传递头文件与编译宏属性建立依赖与继承边不仅链接 .a/.so，更把依赖目标的 PUBLIC/INTERFACE 属性传过来
PRIVATE / PUBLIC / INTERFACE控制属性背包向后传递的可见性范围“传递性三剑客”PRIVATE=仅自己用；INTERFACE=仅别人用；PUBLIC=自己和别人都要用

🔍 为什么坚决不要用 include_directories()？

老式 CMake 的 include_directories() 是全局污染的：一旦在根目录写了一次，所有子目录的所有 Target 都会被强行塞入该路径，极易导致同名头文件互相覆盖撞车，引发诡异的编译错误。现代 CMake 必须使用 target_include_directories()！

🎯 怎么理解 PRIVATE / INTERFACE / PUBLIC？

一句话判定原则：
• PRIVATE：我实现用，我的头文件对外不暴露该类型（下游不用）；
• INTERFACE：我自己不编译（如 Header-only 库），仅为了让依赖我的下游获取配置；
• PUBLIC：我自己实现要用，且我暴露的头文件里包含了对方的类型，下游必须跟着依赖。

🚀 为什么推荐 cmake -B build 目录外构建？

目录外构建（Out-of-source Build）把生成的 Makefile、.o、二进制全部集中在 build/ 文件夹中。只要 rm -rf build 就能一秒得到干净的源码仓库，绝不会把源文件目录搞得乌烟瘴气。
